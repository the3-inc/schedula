# 公式サンプルとの機能差を埋める改修と勤務計画 API 案

開発者が導入時に最適化モデルを書かず、条件変更・不足確認・再計画まで進める入口を設計する。
判断することは、公式サンプルに対する不足をどこで埋め、Python 利用者に何を直接記述してもらうかである。
利用者がまだいないという今回の検討前提で、入口の再設計を提案する。実装済み仕様は変更しない。

推奨は、**JSON 互換の Request / Response を中核に残し、Python ではキーワード引数から Request を作る入口を追加する**こと。
同時に、公式の勤務種別別の回数・連続長・遷移・過剰人数評価を、入口だけでは代替できない機能として扱う。
[詳細対応表](../evaluations/or-tools-shift-scheduling.md)と合わせて実装対象を選ぶ。

## 現状と設計の境界

比較対象は、この checkout の契約0.15と Google の `shift_scheduling_sat.py`。
公式側の固定 commit と schedula 側の調査基点は詳細対応表に記録する。
OR-Tools 全体の能力比較ではなく、公式の特定サンプルと schedula の公開契約の比較である。

現在も `solve(request, num_workers=2)` へ Python の dict/list を直接渡せる。
JSON 文字列化・一時ファイル・CLI の subprocess 呼び出しは必要ない。
公開型は `TypedDict`、値の検査は `validate` / `solve` が担う。
根拠は [Python API](../python-api.md)、[公開 stub](../../src/shift_schedula/__init__.pyi)、
[公開型](../../src/shift_schedula/types.py)、[公開 API のテスト](../../tests/test_public_api.py)。

JSON は保存・他言語との交換形式であり、Python 利用者が全項目を手で書く必要性とは別の問題である。
入口を改善しても、勤務可能時間、履歴、必須条件、目的順序の業務判断は自動で補作しない。

## JSON と引数の選択

| 方式 | 利点 | 負担・制限 | 判断 |
| --- | --- | --- | --- |
| Request の dict を直接渡す現状 | 保存・CLI・HTTP・独立検証で同じデータ。全機能を使える | 版・モード・空配列と入れ子構造を理解する必要がある | 詳細な組み込みの入口として維持 |
| キーワード引数から Request を作る関数 | 引数補完で必要項目が分かり、共通の定型記述を減らせる。返却 Request を保存・編集できる | 業務データの入れ子は残る。簡単な関数だけで公式との差は埋まらない | 最初の追加対象 |
| `solve(employees=..., ...)` に全入力を追加 | 1回の呼び出しで実行できる | 既存 Request 引数との排他条件、構築・検査・探索の責任が重なる。求解前の確認・保存に別入口が必要 | 当初は追加しない |
| `Employee(...)`、`Roster(...)` などのオブジェクト一式 | IDE 補完、日時型、メソッドを使える | dict と別モデルの変換・検証・保存・版管理が必要 | 当初は追加しない |
| CLI に人数・需要・全ルールのフラグを追加 | 極小の例は短くなる | 複数人・複数期間・複数ルールを表すと指定が難しく、履歴や参照も不明瞭 | CLI はファイル/標準入力を維持 |

構成は `キーワード引数 → Request → validate / solve → Response`。
同じ Request を `verify`、`make_baseline`、既存の実行記録へそのまま渡す。
ソルバーを扱う別の実行経路や結果オブジェクトは作らない。

[ADR-0001](../adr/0001-json-first-engine.md)の JSON 境界と両立し、
[ADR-0002](../adr/0002-joint-roster-optimization.md)の勤務・担当の同時最適化も保てる。
[Python API 方針](../python-api.md)の「新しい入力モデルや実行時の型変換は加えない」に対し、
既存の型と値を使う構築関数として位置付け、公開方針へその責任を追記する。

## 既存機能を使いやすくする改修

### Request の構築関数

仮称 `build_roster_request` を、求解せず現在の `Request` を返す純粋な関数として追加する。
以下は未実装の呼び出し案。`employees` などは既存の公開型で作った値であり、新しい業務形式ではない。

```python
request = build_roster_request(
    request_id="restaurant_week",
    planning_window={
        "start": "2026-10-19T00:00:00+09:00",
        "end": "2026-10-26T00:00:00+09:00",
        "timezone": "Asia/Tokyo",
        "slot_minutes": 30,
    },
    employees=employees,
    roles=roles,
    demand=demand,
    skills=skills,
    shift_templates=templates,
    constraints=rules,
    preferences=preferences,
    objectives=objectives,
    solver={"backend": "auto", "time_limit_seconds": 10, "seed": 0},
)
result = solve(request, num_workers=2)
```

最初の責任と既定値は次の範囲に絞る。

| 項目 | 構築関数の扱い |
| --- | --- |
| `request_id/planning_window/employees/roles/demand/solver` | 必須キーワード。値は既存型のまま受け取る |
| `schema_version/problem_type` | 対象の現行版と `roster` を設定する |
| `skills/shift_candidates/constraints/preferences/objectives` | 省略時は新しい空配列を作る。明示値の順序・0を保つ |
| `shift_templates` | 指定時だけ既存形式で設定する。候補の展開は既存処理へ委ねる |
| 従業員の `history/availability` | 自動補完しない。履歴なし宣言も利用者が明示する |
| `minimum_people/priority` | 既存の省略時の意味を保つ。完全充足へ勝手に変更しない |
| その他の任意機能 | 最初の関数に全機能の引数を増やさず、返却 Request の既存欄へ明示設定してから検査・実行する |

`None` を空配列に変換したり、文字列から日時を推測したりしない。
入力をコピーして新しい dict/list を返し、呼び出し側の値を変更しない。
構築成功を検証成功とせず、業務上の受理・不備・環境障害は既存 `validate` / `solve` に集約する。
未知キーワードは関数の引数検査で拒否し、汎用 `**kwargs` による項目の素通しは作らない。

これはトップレベルの定型記述を減らす改修であり、勤務種別別人数の入力を単独で簡略化するものではない。
勤務候補生成は既存 `shift_templates` をそのまま使い、二つ目の日時・休憩展開器を持たない。

### 代表例と説明順序

README の最初の入口を、Python の「構築→計算→状態分岐→不足確認」にする。
CLI・完全 JSON・全機能仕様は、同じ例の別の使い方として続ける。
現状でも dict 直渡しができることは、構築関数の実装前から明記できる。

追加する代表例は次の3本。

1. 固定された勤務テンプレートで計算し、出退勤・休憩・担当配置・不足を読む。
2. 勤務不可区間を変更し、既存 `make_baseline` と変更最小化で再計画する。
3. 返却解を手修正し、`verify` の違反と不足を読む。検証で最適性を付与しない。

例ごとに入力を最初から作り直さず、元 Request を保持した別入力で変更を示す。
実行記録が必要な例では既存 `create_record` を使い、別の保存形式を作らない。

### 影響範囲と受け入れ条件

| 対象 | 改修・確認 |
| --- | --- |
| 新しい構築関数と `__init__.py` / `__init__.pyi` / `types.py` | 既存型による明示引数、公開 export、戻り型。新しい依存は不要 |
| `tests/test_public_api.py` と構築用の小さなテスト | 手書き Request と構築結果の等価性、入力非破壊、返却値と入力の別所有、欠落/空/0/null、未知引数 |
| `examples/`、README、`docs/python-api.md` | 完全なコピペ実行例、状態分岐、履歴宣言、不足許容の既定値 |
| 型・配布検証 | 隔離 wheel の公開 import と mypy consumer。誤った引数を型検査で拒否 |
| CLI・Adapter・デモ | 構築後の JSON を既存入口へ渡して同じ検証結果になる。既存形式は変更しない |

この追加だけなら新しいソルバー制約、JSON Schema、実行記録形式の変更は不要。
同率解の配置そのものの一致を要求せず、受理される条件・評価・有効性が同じことを確認する。

## エンジンで埋める必要がある機能差

以下の識別子は設計案であり、契約0.15で使えるフィールドではない。
単位と必須条件の意味が変わるため、次の契約として Schema・型・求解・独立検証まで同時に設計する。

| 改修対象 | 最小限の意味 | 主な変更箇所 | 受け入れの具体例 |
| --- | --- | --- | --- |
| 排他的な勤務種別の選択と固定 | 従業員・ローカル開始日ごとに休みまたは一つの勤務種別。候補に安定した種別参照を持つ。特定種別と休みの固定を基準計画なしで指定 | Schema、型、候補生成/正規化、CP-SAT、独立検証、解の種別参照 | 同じ時刻・長さの二つの種別も別扱い。固定された休みには候補を選ばない |
| 種別別の回数上下限と望ましい範囲 | 明示期間の選択回数に hard 下限/上限、soft 下限/上限、片側ごとの整数ペナルティ | 回数条件、目的式、独立回数集計 | 夜勤は0〜4回まで許容し、1回未満だけ罰する。2〜3回を望む場合は両方0点 |
| 種別別の最大連続区間 | 同じ種別が続く最大区間ごとに hard / soft 上下限。休みも日別の選択として対象にできる | 連続区間の検証/モデル/評価、期間端と履歴の意味 | 夜勤1〜4連続を許容、2〜3連続を望む。夜勤1回に20点、4回に5点 |
| 勤務種別の並びの選好 | 明示した日差の種別ペアの発生ごとに整数ペナルティ。禁止は別の必須条件 | パターン、選好、目的、独立集計 | 遅番→夜勤に4点。夜勤→早番は禁止。重み0を禁止の代用にしない |
| 勤務種別ごとの人数と超過評価 | 日付・種別ごとの選択人数の必須下限と、超過1人ごとの整数ペナルティ | 新しい勤務人数集計、求解、Response/verify | 朝番の最低2人を守り、3人なら超過1人。役割担当2人＋待機1人でも選択人数は3人 |
| 選好の点数内訳と合計 | 種別希望・回数・連続長・並び・超過人数を整数のイベント点数として加算 | 新しい評価 metric、整数上界、内訳と独立再計算 | 20点の連続長違反と4点の並び違反を、同じ合計点で比較できる |

現行の `shift_categories` は区間の重なりによる多重分類であり、排他的な勤務種別を表す代用にはしない。
現行の `shift_count_deviation` は単点への絶対偏差であり、帯域内0点・片側ごとに異なる傾きの代用にはしない。
現行の `scheduled_minutes` / `scheduled_cost` は超過人数の件数評価の代用にはしない。
根拠は [現行契約](../io-contract-current.md)、[勤務分類](../../src/shift_schedula/shift_patterns.py)、
[回数評価](../../src/shift_schedula/shift_counts.py)、[CP-SAT](../../src/shift_schedula/cp_sat.py)。

### 公式と同じ評価と、schedula の目的順序を両立する

既存の目的全体を重み付き合計へ変更することは推奨しない。
新しい勤務選好を集約する一つの metric（仮称 `shift_penalty`）の内部で、明示された整数点数を合計する案を推奨する。
その metric と既存の勤務量・費用・変更量の間には、従来の目的順序を使う。
これは [設計方針](../design-policy.md)の「上位目的を巨大な暗黙重みで代用しない」と両立する。
ただし、選好の単位と加算範囲は新しい契約・設計判断へ明示し、既存 `preference_penalty` の分単位の意味を変えない。

公式相当の比較では、すべての対象ペナルティをその一つの metric に入れ、勤務種別人数の下限を必須にする。
役割需要を併用するなら完全充足を要求し、需要不足との意図しない優先関係を除く。
比較目的にない勤務量・費用・公平性を追加して、公式と同じ最適化だと説明しない。

負の希望報酬は、希望する選択をしなかった場合の正のペナルティへ変換する方式も可能だが、
その場合は定数差を内訳に記録する必要がある。最適な選択が同じでも元の目的値とは一致しない。
公式との値比較では、同じ元の点数定義から独立に再集計する。

### 期間端と休みの定義

公式の `O` は日次の休みという選択肢で、公式ファイルには勤務の時計時刻がない。
勤務種別を開始日へ帰属させて移植するなら、夜勤明けでも新しい勤務開始がない日を `O` へ写像し得る。
schedula の「完全休日」は原勤務区間が一度も触れない日で、この写像とは夜勤で一致しない。
公式と同じ日別表を使う入口では `O` 相当の状態を明記し、法令上の休日や完全休日と表示しない。

公式サンプルは有限の配列端を連続区間の端として扱う。
同じ問題を再現する閉じた期間と、過去実績・既知の確定勤務を引き継ぐ継続計画では境界条件が異なる。
サンプル再現の利用者宣言と、実運用の確認済み文脈を区別し、履歴を勝手に空へ置換しない。
夜勤・分割・休憩を加えた場合も、勤務種別の回数と実経過分数を分けて検証する。

## 勤務種別から始める簡単な入口

上記の勤務種別と人数の契約を決めた後、仮称 `build_shift_roster_request` を検討する。
関数名と形状は未実装案。固定された時刻の勤務種別を使う問題を対象にし、すべての勤務計画を一つの簡易形式へ押し込めない。

| 利用者が渡すもの | 入力で明示する内容 | ライブラリが行うこと |
| --- | --- | --- |
| 期間 | 開始日、終了日、timezone、粒度 | ローカル日付を列挙 |
| 従業員 | ID、勤務可能時間、確認した履歴 | 指定した勤務種別の対象者との参照確認 |
| 勤務種別 | ID、開始時刻、勤務区間長、休憩、対象者 | 既存テンプレートの構築と候補生成への接続 |
| 必要人数 | 日付または曜日、種別、必須人数、任意の超過係数 | 指定期間へ展開し、重複や衝突を拒否 |
| 固定・希望・ルール | 対象者、日付/期間、種別、必須/望ましい範囲と点数 | 共通 Request の条件へ対応付ける |

必要人数を役割別需要に自動変換しない。勤務種別の選択人数と、休憩を除く時間帯の担当人数は別である。
技能・時間帯別需要・役割を併用する利用者は詳細 Request を使えるようにする。
両入口とも同じエンジンと検証器を使い、簡易入力から変換した Request と項目対応を確認・保存できるようにする。

曜日繰り返しなどの短縮形を導入する場合は、その公開型と入力規則を別途定める。
クラス階層や専用の求解器は不要だが、業務意味を持つ新しい短縮形の検証責任は省略できない。
現行 Adapter の `assemble` は確認済み値を結合する境界なので、短縮形展開と新しい業務判断を混在させない。

## 実装の順序と完了の判断

| 実装単位 | 先に完成させる理由 | 完了を判断する証拠 |
| --- | --- | --- |
| Python の構築入口と3つの代表例 | 既存の価値を少ない改修で使える。機能追加を待たずに改善できる | 手書き/構築/保存往復で同じ条件、型付き consumer、求解・再計画・検証例 |
| 勤務種別・回数・連続長・並び・人数・点数の契約 | 公式の機能差を入口だけで隠さず埋める | 各条件の小規模全列挙、独立検証、改ざん拒否、下記の公式相当比較 |
| 勤務種別の簡易入力 | 上記の意味を短く入力できるようにする | 簡易入力と明示 Request が同じ許容計画・評価を持つ。境界の不足を拒否 |

エンジン拡張は新契約の入力/出力 Schema、`types.py`、正規化、CP-SAT、`verify`、
baseline/固定、診断、Adapter、記録、CLI、デモの利用側、配布型、例・fixture を対象にする。
[サポート方針](../contract-support.md)に従い、保存データと利用アプリの対応を実装時に確認する。
今回の未利用という前提は設計の自由度に使い、既存例・保存記録・利用アプリを無条件に削除する根拠にはしない。

公式相当比較の受け入れは、固定された8人・21日の公式入力に対して行う。
勤務時刻・日付・種別の解釈、配列端、固定、点数定義を明示して両方へ同じ条件を渡す。
両方で最適性が証明できた場合のみ最適目的値を比較し、時間切れなら値・境界・証明状態を並べる。
同率解の勤務表の完全一致や、公式より高速という主張は完了条件にしない。
また、縮小した入力を独立全列挙して、許容計画と点数が一致することを確かめる。

使いやすさは、初見の開発者が「最初の計算」「希望追加」「欠勤後の再計画」を、
内部のモデルコードを読まずに行えるかで確認する。
記述量・所要時間・質問や修正が必要だった箇所を残し、機能数だけで使いやすいと判定しない。
